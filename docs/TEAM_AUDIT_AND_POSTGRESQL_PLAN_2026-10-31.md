# Аудит CRM College и план работ команды

Дата: 31.10.2026. Проверенная версия: `67bd9d6`. Назначения в этом документе — предлагаемые задачи команде; уведомления и задачи во внешних системах не отправлялись. Оценка основана на репозитории и локальных проверках, без проверки действующего сервера и реальных данных.

## Что уже есть

- Vue 3/Vite/Pinia: интерфейсы входа, администрирования, расписания, аудиторий, групп и технологических карт; тесты Vitest.
- Три FastAPI-сервиса: авторизация и пользователи, расписание и связанные сущности, технологические карты и генерация документов. Есть SQLAlchemy-модели и наборы pytest; наличие кода само по себе не подтверждает работоспособность каждого сценария.
- Docker Compose, Nginx, контейнер PostgreSQL с постоянным томом и инициализацией трёх баз. Auth поддерживает PostgreSQL через настройку, schedule — при наличии настроек хоста и порта. Techcard фактически использует SQLite.
- Есть отдельные инструкции и исторические отчёты. Общего актуального README в корне и отслеживаемых миграций Alembic не обнаружено.

## Переход с SQLite на PostgreSQL

**Текущее состояние:** auth по умолчанию использует SQLite, в Compose настроен PostgreSQL; schedule выбирает SQLite для локального запуска и PostgreSQL при настроенных параметрах; techcard всегда использует файловый SQLite вне `TESTING=1`. Следовательно, работа охватывает не только смену конфигурации, но и перенос фактических данных всех окружений, где ещё есть SQLite. `docs/POSTGRESQL_MIGRATION.md` не является подтверждением завершённой миграции.

1. **Инвентаризация — Глеб, Ярослав.** Для каждого окружения определить используемые базы и файлы SQLite, их владельцев, версии схем, объёмы, доступное окно остановки и требования к восстановлению. Проверить, не находятся ли ценные данные techcard только внутри существующих контейнеров. Не пересоздавать их до подтверждённой копии.
2. **Резервные копии — Глеб, Ярослав.** Согласованно остановить запись или использовать согласованный механизм снимка SQLite, учитывающий WAL. Сохранить копии вне контейнеров; проверить открытие копий и восстановление в изолированном окружении. Для уже используемых PostgreSQL-баз также сделать и проверить резервные копии.
3. **Схема и инфраструктура — Глеб, Ярослав, Артём.** Согласовать целевые БД и роли с минимальными правами, подготовить версионируемые миграции и настройку подключения techcard. Проверить совместимость типов, дат и времени, ограничений, внешних ключей, уникальности, автоинкрементных последовательностей и кодировки. Согласовать соответствие пользователей и связанных ID между сервисами.
4. **Репетиция — Глеб ведёт, вся команда участвует.** Перенести копии данных в отдельный PostgreSQL; сохранить идентификаторы и связи; выставить последовательности после загрузки. Сверить количество строк по таблицам, ключевые поля и связи, проверить ограничения и бизнес-сценарии входа, расписания и карт. Зафиксировать расхождения и длительность переноса, повторять до успеха.
5. **Переключение — Ярослав ведёт, Глеб и Артём участвуют.** Объявить окно, остановить запись, снять финальные копии, выполнить проверенную миграцию, сверить результаты и включить сервисы на PostgreSQL. Выполнить smoke-тесты через gateway и проверить сохранение данных после пересоздания контейнеров.
6. **Откат и завершение — вся команда.** До запуска определить условие отказа и момент принятия решения; при неудаче до возобновления записи вернуть прежнюю конфигурацию и проверенные копии. Если запись в PostgreSQL уже началась, простой возврат к SQLite потеряет новые изменения: остановить запись и применить заранее проверенную процедуру обратного переноса либо восстановить по согласованной точке. Не удалять исходные копии до завершения периода проверки и согласования владельцем данных.

## Порядок работы

- **Сразу параллельно:** Артём — T1 и T4; Ярослав — T3 и проверка доступности; Глеб — инвентаризация и копии T2. Тесты доступа и сохранности делать вместе с исправлениями.
- **Следом:** Глеб ведёт T2/T5; Ярослав готовит PostgreSQL, восстановление и T9; Артём согласует контракты и выполняет T6/T7. Схему пользователей и API согласовать до параллельной реализации.
- **Затем:** команда закрывает T8, T10 и T11; CI и документацию поддерживать по мере исправлений.

## Результаты и границы проверки

- `npm run build` — успешно; `npm test -- --reporter=dot` — 13 прошли, один упал в `src/store/__tests__/admin.spec.js` на отсутствующем `store.auditLogs`.
- `docker compose config --quiet` — успешно; это проверка конфигурации, а не запуска контейнеров или доступности сервисов.
- Backend-тесты не запускались: в доступном `python3` не установлен pytest. Особенно важно сначала устранить опасность `drop_all` в тестах techcard.
- Эксплуатационное окружение, реальные записи, резервные копии, безопасность всех маршрутов, зависимости на известные уязвимости и весь пользовательский функционал не проверены. Приоритеты относятся к найденным рискам, а не к гарантированному списку всех дефектов.
