# Аудит CRM College — 12 ноября 2026

Область: исходники ветки `arena/fa96b676-crm-college` на базе `1ce78ef`, frontend, три FastAPI-сервиса, общий пакет, конфигурация gateway/Compose, миграции и тесты. Это **аудит кода и локальных in-memory сценариев**, а не пентест развёрнутого окружения. Реальные настройки TLS, бэкапы, пользовательские данные, нагрузку и PostgreSQL-контейнеры здесь не проверяли. Тестовые адреса в описании — синтетические.

## Как устроен проект

Browser → Nginx (`/api/auth`, `/api/users` → auth; `/api/schedule`, `/api/relations`, `/ws` → schedule; `/api/techcards` → techcard; остальное → Vue SPA). Auth выдаёт подписанные HS256 access/refresh JWT в cookie; schedule/techcard сами проверяют access JWT по общему `SECRET_KEY`. Данные разнесены по трём БД PostgreSQL; отдельные SQLite-пути используются локально/в тестах. Frontend — Vue 3/Pinia/Axios, роуты лениво загружаются. Плюсы: рабочие миграции и health checks, общая точка входа, базовые RBAC-проверки для записей расписания, owner-check чтения техкарт, HttpOnly/SameSite cookies, origin-check WebSocket, CI и юнит-тесты. Но важные контракты между частями не согласованы.

## Приоритет P0 — устранять перед публикацией реальных данных

### 1. Анонимный доступ к персональным данным участников — подтверждено

`backend/schedule/routers/participants.py:15-17` не требует аутентификации. `backend/schedule/api/participants_api.py:10-16` отдаёт список пользователей по известному `group_id`; `backend/schedule/database/models.py:125-135` включает в ответ **email, ФИО и telegram_id**. Gateway проксирует этот путь: `nginx/nginx.conf:52`.

**Воспроизведено** на TestClient с in-memory БД: GET `/api/schedule/participants/1/participants` без cookie/заголовка вернул `200` и перечисленные поля для тестового участника. Если schedule БД содержит реальные записи, эти данные могут собрать посторонние, в том числе через туннель. Действие: закрыть маршрут авторизацией и политикой доступа по группе; для публичного расписания сделать отдельное представление *без* PII; добавить тесты «аноним 401 / чужая группа 403 / владелец или уполномоченный 200».

### 2. «Личный» календарь включает чужие занятия — подтверждено

`backend/schedule/routers/calendar.py:9-12` принимает authenticated `user`, но `backend/schedule/services/calendar_service.py:7-12` не использует `user_id` и запрашивает до 1000 **всех** занятий. Воспроизведено: access JWT тестового пользователя `999`, не являющегося участником, получил `200` на `/api/schedule/calendar/me.ics`; ответ содержал занятие другой группы. Исправить через явную связь пользователь ↔ участник/группа/преподаватель; проверить отсутствие чужих событий и согласовать, что вообще считается «моим расписанием».

### 3. Авторизованный студент создаёт техкарту через API, несмотря на скрытый UI — подтверждено

В `backend/techcard/routers/techcard_router.py:106-128` есть `Depends(get_current_user)`, но нет проверки роли для создания; `backend/techcard/auth.py:17-60` проверяет подпись и claims, не разрешённые роли. В интерфейсе ссылка скрыта для студентов (`frontend/src/core/layouts/DefaultLayout.vue:73`), но `/techcards` и `/techcards/:id` требуют только вход (`frontend/src/router/index.js:55-65`). Воспроизведено: JWT с `role=student` и POST `/api/techcards` вернул `201`. Если по бизнес-правилам техкарты доступны только преподавателям/админам, это обход прав. Добавить проверку роли для create/list/get/update/download и серверные тесты по матрице ролей. Если студентам создавать карты разрешено — закрепить это в требованиях и UI; сейчас контракт противоречив.

## Приоритет P1 — безопасность и корректность основных сценариев

### 4. Создание пользователя администратором подменяет сессию администратора — подтверждено

Frontend вызывает регистрацию в `frontend/src/store/admin.js:86-90`. Обработчик `backend/auth/routers/auth.py:27-70` одновременно создаёт аккаунт, выпускает **его** токены и устанавливает их в cookie текущего браузера (`:56-60`). Воспроизведено: администратор логинится, POST `/api/auth/register` создаёт студента, после чего GET `/api/auth/me` в том же клиенте возвращает **нового студента**. Список пользователей сразу после создания перестаёт открываться, интерфейс хранит старый профиль до обновления. Создать отдельный защищённый `POST /api/users` для администраторов, возвращающий `UserResponse` без `Set-Cookie` и без выпуска refresh-токена; публичная `/register` должна аутентифицировать только самого регистрирующегося.

### 5. Немедленный отзыв прав и сессий не работает для уже выпущенного access JWT

Auth при изменении роли/деактивации и смене пароля отзывает refresh-токены (`backend/auth/routers/users.py:99-106`, `backend/auth/routers/auth.py:195-201`), но schedule/techcard проверяют только подпись, срок и роль из **старого** access JWT (`backend/schedule/dependencies.py:9-38`, `backend/techcard/auth.py:37-60`). Auth тоже не проверяет session revocation для access-токена (`backend/auth/dependencies.py:55-77`). В итоге уже выданный JWT продолжит работать до `ACCESS_TOKEN_EXPIRE_MINUTES` (по умолчанию 15) даже после разлогина/отзыва прав, если попадёт к другому клиенту. Уточнить SLA отзыва; добавить `session_id`/`token_version` с общей проверкой статуса или короткий TTL + проверку для критичных действий, тесты на смену роли и отзыв.

### 6. Токены выдаются в JSON, хотя браузерная схема заявлена как cookie-only

`backend/auth/database/schemas.py:73-78`, `backend/auth/routers/auth.py:65-69,99-104,134-139` возвращают access **и refresh** в теле ответа на login/register/refresh; cookies при этом HttpOnly (`backend/auth/services/cookie_service.py:16-35`). Frontend токены не сохраняет, но они доступны JS в `response.data`, DevTools, proxy-инструментам и любому внедрённому скрипту. Это **не равно доказанной XSS**; это лишняя поверхность утечки и несоответствие объявленной модели. Для browser API возвращать только профиль/срок, отдельный явно оговорённый token endpoint оставить лишь при необходимости внешних клиентов. Refresh хранится в БД целиком (`backend/auth/database/models.py:58`, `backend/auth/services/token_service.py:24-29`) — хеширование уменьшит ущерб при утечке БД.

### 7. Данные расписания: импорт и редактирование не сохраняют важные инварианты

В `backend/schedule/api/slots_api.py:23-39,50-68` доступность аудитории проверяется как read-then-write без блокировки/DB-ограничений; конкурентные запросы могут назначить один кабинет одновременно. Не проверяется `end_time > start_time`, пересечение занятий одной группы/преподавателя, существование аудитории при её указании; схема `backend/schedule/database/models.py:174-205` этих правил тоже не вводит. Импорт `backend/schedule/services/schedule_importer.py:65-129,207-248` пишет напрямую, минуя проверку конфликта, продолжает после ошибок отдельных строк и возвращает `status=success` с `errors`; статистика создания групп/аудиторий проверяется **после `flush`**, когда `id` уже присвоен (`:68-79,137-162`), поэтому счётчики новых сущностей неверны. Нужны транзакционная политика импорта, предварительная валидация, DB-ограничения/блокировки или serializable retry и тесты конкурентности/частичных ошибок.

### 8. Несогласованная модель пользователей и справочников в трёх БД

В auth есть пользователь с ролью и статусом (`backend/auth/database/models.py:24-34`), в schedule — отдельная таблица `users` с `email`, `password_hash`, `telegram_id` без роли (`backend/schedule/database/models.py:20-28`), в techcard — `owner_id`, `group_id`, `teacher_id`, `lesson_id` как числа без FK в другие сервисы (`backend/techcard/database/models_techcard.py:12-19`). `backend/schedule/routers/notifications.py:15-20` ищет schedule-пользователя по `user_id` из JWT auth; механизм синхронизации этих записей в рассмотренном потоке регистрации не найден (`backend/auth/routers/auth.py:49-70`). Риск: подписка возвращает 404, «мои» данные разъезжаются, техкарты ссылаются на несуществующие группы/уроки. Договориться об источнике истины, идентификаторах и синхронизации (outbox/сервисные вызовы с retries), написать интеграционные тесты регистрации/удаления/обновления.

### 9. Кэш расписания и WebSocket не дают гарантии актуальности

`backend/schedule/routers/schedule.py:48-67` кэширует список 30 сек, `backend/schedule/routers/groups.py:15-19` — группы 60 сек, но мутации (`schedule.py:19-46,73-98`, `groups.py:21-42`) не инвалидируют кэш. WebSocket-клиент после события заново вызывает endpoint (`frontend/src/features/schedule/views/ScheduleView.vue:245-252`), который может вернуть старое значение. InMemoryBackend (`backend/schedule/main.py:63-70`) живёт только внутри процесса; менеджер соединений тоже in-memory (`backend/schedule/services/websocket_manager.py:7-39`) и не доставит события между инстансами. Для текущего одного контейнера — TTL-окно; при масштабировании — межпроцессный разрыв. Ввести явную инвалидацию и общий broker/cache либо оставаться на одном процессе с зафиксированным ограничением.

### 10. Ограничение затрат и ошибок API недостаточно строгое

`backend/schedule/routers/schedule.py:50-67` принимает `limit <= 2000`, но `backend/schedule/api/schedule_api.py:110-113` **игнорирует `limit` при любом `date_from/date_to`** и возвращает до 2000 строк, а возвращаемый порядок — по убыванию времени. Экспорт доступен без аутентификации (`backend/schedule/routers/export.py:9-20,36-45`), создание XLSX/PDF выполняет запросы и формирование документа (`backend/schedule/services/schedule_exporter.py:83-118,159-205`) без ограничений диапазона и частоты. Возможно публичный экспорт задуман; тогда нужны ограничения диапазона, объёма и rate limit на gateway/сервисе. Загрузка Excel (`backend/schedule/api/schedule_api.py:24-38`) читает файл целиком и синхронно парсит его внутри async-endpoint; gateway ограничивает тело 20 МБ (`nginx/nginx.conf:11`), но xlsx может разжиматься в гораздо больший объём. Лимитировать размер/ячейки, парсить в worker/thread pool, ограничить частоту. В `backend/schedule/api/schedule_api.py:58-63` и `backend/techcard/routers/techcard_router.py:170-172,220-222` текст внутренних исключений возвращается клиенту: оставить детали в серверном логе, клиенту давать общий код/сообщение.

## Frontend: устойчивость, UX, контракты

- **Авторизация.** `frontend/src/store/auth.js:58-65` в `bootstrap()` молча проглатывает ошибку `/auth/me` и не очищает ранее сохранённый `user`; `isAuthenticated` = `!!user` (`:25-28`). При сетевой ошибке/503 либо отказе refresh не всегда срабатывает логика интерцептора `frontend/src/core/utils/api.js:23-50`; маршруты и меню могут временно показывать устаревшую роль. Это не серверный bypass, но неверное состояние UI. Нужны состояния `unknown/authenticated/unauthenticated/offline`, сброс/переоценка профиля и тесты ошибок bootstrap. Интерцептор делает глобальную навигацию `window.location.href='/'`, что рвёт текущую работу.
- **Группы и автозаполнение.** `frontend/src/features/schedule/views/ScheduleView.vue:208,323-331` начинает с `selectedGroupId=1`; если группы с ID 1 нет, пользователь видит пустое расписание. `frontend/src/features/techcards/views/TechcardEditorView.vue:271-280` подставляет `selectedLesson.group_id`, однако `/api/schedule/list` не выбирает `group_id` (`backend/schedule/api/schedule_api.py:81-91`); автозаполнение группы на этом ответе не работает. Согласовать typed response-контракт и выбирать первую доступную/свою группу.
- **Временные зоны и даты.** `frontend/src/store/schedule.js:54-60`, `frontend/src/features/schedule/views/ScheduleView.vue:299-304,323-330` применяют `toISOString().split('T')[0]` к локальным датам. ISO — UTC; около местной полуночи в UTC+5 это может дать предыдущий день (и даже неделю). Перейти к форматированию календарной даты в локальной зоне/явной зоне колледжа и тестировать границы суток. Backend хранит `ClassSlot.start_time/end_time` без timezone (`backend/schedule/database/models.py:90-91`); зафиксировать семантику времени сквозным контрактом.
- **Порядок и гонки.** `backend/schedule/api/schedule_api.py:111` сортирует занятия по убыванию; `frontend/src/features/dashboard/views/DashboardView.vue:98-100` берёт первые три как «ближайшие», не исключая уже прошедшие. Одновременные `fetchSchedule` при смене недели, группы и WebSocket могут перезаписать более новый результат поздним ответом (`frontend/src/store/schedule.js:37-44`, `ScheduleView.vue:245-252,404-410`). Использовать серверную сортировку/фильтр upcoming и отмену старых запросов/sequence id.
- **Техкарты и отклик.** `frontend/src/store/techcard.js:17-27` глотает ошибку списка; `TechcardsListView.vue:59-66` показывает «нет карт» даже при отказе API. Пагинация API (`backend/techcard/routers/techcard_router.py:93-103`) в UI не реализована, после 50 записей остальные не видны. `downloadCard` создаёт ObjectURL и не отзывает его (`frontend/src/store/techcard.js:75-82`). Нужны error/empty/loaded состояния, кнопка «следующая страница» и `URL.revokeObjectURL`.
- **Доступность и адаптивность.** `frontend/src/core/components/BaseModal.vue:4-28` не задаёт `role="dialog"`, `aria-modal`, управление фокусом/Escape и возврат фокуса; кнопки-иконки без `aria-label` (`frontend/src/features/schedule/views/ScheduleView.vue:74-75,104-109`). Есть breakpoint для колонок расписания (`ScheduleView.vue:760-769`), но общая оболочка имеет фиксированный sidebar 260px/84px и `width:100vw` (`frontend/src/core/layouts/DefaultLayout.vue:89-109`), а `html,body` скрывают overflow (`frontend/src/core/styles/main.css:37-44`). Проверить реальные мобильные размеры и клавиатурную навигацию, не объявлять интерфейс адаптивным лишь по одному breakpoint.
- **Демонстрационные значения вместо данных.** `frontend/src/features/dashboard/views/DashboardView.vue:71-78` подставляет `ИСП-21` при отсутствии группы; `:48-49` подставляет аудиторию `201`. Пользователь видит неправду; отображать «не указано» и явно моделировать связь с группой.

## Эксплуатация, качество и долги

- `backend/auth/main.py:20-24`, `backend/schedule/database/database.py:55-56`, `backend/techcard/main.py:12-16` вызывают `create_all` при старте. Он не обновляет существующие таблицы и не заменяет Alembic; может скрыть пропущенную миграцию на пустой БД. Выделить миграции в обязательный deploy step, на старте проверять revision; тестировать переходы с живых схем и восстановление из бэкапа.
- `backend/auth/middleware/rate_limit.py:13-20,73-85` — процессный per-IP rate limiter только auth; общий лимит 100/мин не отличает login от чтения, `X-Real-IP` доверяется без проверки доверенного прокси (безопаснее при текущей непубликуемой сети Compose). Для публичного deployment нужен единый ingress rate limit и выделенный лимит входа. Cookie-auth state-changing запросы не имеют явного CSRF-токена/Origin-check (`backend/auth/services/cookie_service.py:16-35` и write routers). `SameSite=Lax` сокращает обычную cross-site угрозу, но нужно проверить same-site поддомены/будущую конфигурацию; это риск модели, не доказанная эксплуатация.
- `backend/schedule/services/notifications.py:26-31` содержит старую неиспользуемую функцию с `with get_db() as conn` и `.cursor()` (текущий `get_db` — generator SQLAlchemy Session); если вызвать, не сработает. Наличие нескольких версий контрактов и «мертвого» кода повышает риск регрессий. `backend/common/crm_auth/verify.py` есть, но schedule/techcard вручную повторяют проверки (`backend/schedule/dependencies.py:9-38`, `backend/techcard/auth.py:17-60`). Централизовать одно правило проверки токена и ролей.
- CI (`.github/workflows/ci.yml`) включает frontend lint/format/unit/build, backend lint/coverage, Compose smoke и dependency/secrets scans. E2E `frontend/e2e/smoke.spec.js:3-8` проверяет только HTTP status/#app — не проверяет логин, роли, регистрацию, импорт и скачивание. Настоящие интеграционные тесты (PostgreSQL + gateway + браузер) нужны в PR-пайплайне хотя бы для нескольких критичных путей. `pyproject.toml:16-25` отключает F401 и часть правил; ESLint выдаёт warnings, CI не блокирует их.
