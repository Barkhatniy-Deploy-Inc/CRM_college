# PostgreSQL: локальная работа и восстановление

Инструкция для Глеба и Ярослава. Это окружение разработки: использовать тестовые данные. При первичной инициализации контейнер создаёт три отдельные базы и volume `crm_college_postgres_data`; `docker compose down` не удаляет volume. Не используйте `down -v` для рабочей базы. Инициализация действует только для нового volume: изменение имён, пользователя или пароля в `.env` не меняет уже созданные базы или пароли.

## Запуск и доступ

```bash
./scripts/local.sh init
./scripts/local.sh migrate
docker compose ps db
```

`migrate` требует Docker и собирает образы сервисов. При отсутствии доступа к registry сборка может потребовать повторного запуска после восстановления сети. Команда применяет миграции к базам, заданным в `.env`; к существующим базам применять только после резервной копии и проверки схемы. Не делать `alembic stamp head` для неизвестной схемы. Для старой базы, созданной через `create_all`, см. [инструкцию о baseline](LOCAL_DEVELOPMENT.md#alembic-и-существующие-базы).

Подключение из контейнера PostgreSQL (без публикации сетевого порта):

```bash
docker compose exec db sh -c 'exec psql -U "$POSTGRES_USER" -d "$AUTH_DB_NAME"'
docker compose exec db sh -c 'exec psql -U "$POSTGRES_USER" -d "$SCHEDULE_DB_NAME"'
docker compose exec db sh -c 'exec psql -U "$POSTGRES_USER" -d "$TECHCARD_DB_NAME"'
```

Внутри сети Compose сервер `db:5432`; контейнеры используют заданные имена и настройки `.env`. При необходимости подключения локального GUI запускайте только loopback debug override:

```bash
docker compose -f docker-compose.yml -f docker-compose.debug.yml up -d db
```

Хост `127.0.0.1`, порт `DB_PUBLISHED_PORT` (по умолчанию `5432`), пользователь и пароль из своего `.env`, имя базы из `AUTH_DB_NAME`, `SCHEDULE_DB_NAME` или `TECHCARD_DB_NAME`. Не пересылайте `.env` и не коммитьте его. Все три сервиса пока используют общую учётную запись PostgreSQL с расширенными правами; разделение ролей и защищённое хранение секретов обязательно для будущего production.

## Резервная копия

```bash
mkdir -p backups
python3 scripts/postgres_backup.py backups/initial-2026-10-31
```

Последний аргумент — ещё не существующий каталог; повторное использование отклоняется, поэтому подставляйте новое имя. Скрипт создаёт каталог с правами 0700 и `auth.dump`, `schedule.dump`, `techcard.dump`, `manifest.json` с правами 0600. Успех подтверждается только при завершении команды с кодом 0 и наличии manifest; прерванный каталог нельзя считать копией. `backups/` и `*.dump` исключены из Git. Файлы содержат реальные данные: храните копии за пределами машины и задайте периодичность, хранение и доступ по требованиям владельца данных.

Это три отдельных `pg_dump` (custom format), каждый согласован внутри своей базы. Между базами единая точка во времени не гарантируется: для согласованной копии остановите запись всех сервисов на время копирования или согласуйте другой механизм снимка. Роли и глобальные настройки PostgreSQL эти архивы не включают; сохраните их отдельно, если они потребуются. PostgreSQL volume сам по себе не является резервной копией.

## Проверка восстановления в новую базу

Запускайте при работающем `db`; команда `createdb` завершится ошибкой, если целевая база уже существует, а `&&` не даст выполнить восстановление поверх неё. Выберите свободное имя; ниже проверяется архив auth:

```bash
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" crm_restore_auth' && \
  docker compose exec -T db sh -c 'pg_restore --exit-on-error --no-owner --no-privileges -U "$POSTGRES_USER" -d crm_restore_auth' < backups/initial-2026-10-31/auth.dump

docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d crm_restore_auth'
```

Аналогично проверяйте `schedule.dump` и `techcard.dump` в новых базах с другими именами. Сверяйте таблицы, миграционную версию, количество записей и связи; сохраните протокол проверки. Восстановление в существующую рабочую базу, переключение приложения и обратный перенос после новых записей требуют отдельного согласованного плана. Для повторяемой автоматической репетиции используйте `scripts/test_postgres_backup.sh` только с отдельным одноразовым Compose-проектом `crmtest*` и `PG_BACKUP_TEST_ALLOW=1`: тест создаёт таблицы и базы.

## Состояние миграции SQLite

Схемы Alembic можно создать на пустом PostgreSQL, но команды выше не копируют SQLite. Глебу сначала нужно найти и скопировать исходные базы с учётом WAL, затем согласовать отображение пользователей/владельцев, перенести копию, проверить количества и связи, последовательности и восстановление. Исходные базы сохраняются до принятия результата.
